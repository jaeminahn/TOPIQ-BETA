## SEC-001: 새 익명 세션으로 결과 이메일 발송 제한 우회

- 원본 finding ID: `csf_d0fa7878329686880298751d`.
- 근거: [발송 사용량 집계](../../backend/src/email/usage-repository.ts) 36–45행, [공개 라우트](../../backend/src/routes/public-routes.ts) 23–28·94–124행, [시험 저장소](../../backend/src/exam/repository.ts) 603–613·667–735행, [Brevo 발송](../../backend/src/email/brevo-result-email.ts) 89–104행.

### 원인과 영향

공개 `POST /v1/sessions`는 계정 인증 없이 새 세션과 토큰을 발급합니다. 사용자는 자기 세션을 미응답 상태로 제출한 뒤 형식에 맞는 임의 수신자 이메일로 결과 발송을 요청할 수 있습니다.

시간당 발송량은 `session_id`로만 집계됩니다. 같은 수신자라도 새 세션을 생성하면 세션별 사용량이 다시 0이 되어 반복 발송이 가능합니다. 원치 않는 메일 발송, 발신자 평판 저하, 정상 사용자가 이용하는 공용 월간 발송량 소진으로 이어질 수 있습니다.

기존 제한인 세션당 시간당 5회, 월간 총량 5,000회, IP당 분당 240회 요청 제한은 남아 있습니다. 따라서 무제한 발송·비용 발생으로 해석해서는 안 됩니다. 이 제한들은 세션 교체에 따른 수신자별 남용을 막지 못합니다.

### 개선 방향

- 정규화한 수신자 기준의 세션 간 발송 제한과 재발송 대기시간을 추가합니다.
- 요청자 또는 신뢰할 수 있는 IP 기준 제한을 함께 적용합니다.
- 동시 요청에서도 우회되지 않도록 사용량 확인과 예약을 원자적으로 처리합니다.
- 필요하면 발송 전 자동화 방지 절차를 추가하고 기존 월간 총량 제한을 유지합니다.

### 완료 판단

- [ ] 서로 다른 세션에서 같은 수신자로 요청해도 공유 제한이 적용된다.
- [ ] 동시 요청이 한도를 넘겨 예약되지 않는다.
- [ ] 정상 재발송과 월간 한도 동작이 유지된다.
- [ ] 실패·취소된 발송의 원장 처리 및 재시도 정책을 확인했다.
- [ ] 수정 커밋과 검증 결과를 아래 변경 이력에 기록했다.

현재 검증은 소스 추적과 기존 테스트 읽기만 수행했습니다. `backend/tests/unit/email-usage.test.ts`는 세션별·월간 제한을 다루며 교차 세션 수신자 제한 검증은 없습니다.

## SEC-002: 최초 관리자 설정이 이메일이 같은 기존 계정을 자동 승격

- 원본 finding ID: `csf_229ba06c1e039a71024634ac`.
- 근거: [관리자 초기화](../../backend/src/bootstrap-admin.ts) 20–38행, [관리자 권한 확인](../../backend/src/admin/auth.ts) 26–43행, [로컬 Supabase 설정](../../supabase/config.toml) 175·220–225행.

### 원인과 성립 조건

관리자 초기화는 Supabase 사용자 목록에서 `ADMIN_EMAIL`과 이메일이 같은 기존 계정을 찾으면 그 `auth_user_id`를 활성 관리자 목록에 추가합니다. `ADMIN_PASSWORD`는 새 계정을 만드는 분기에만 적용되며 기존 계정의 소유권을 별도로 확인하지 않습니다.

공격자가 이메일 소유 증명 없이 예정된 관리자 이메일로 먼저 가입하고, 이후 운영자가 최초 관리자 초기화를 실행하면 공격자 계정이 관리자 권한을 얻을 수 있습니다. 성립 시 콘텐츠 관리, 데이터 내보내기·삭제, 유료 생성 작업 등 관리자 기능에 영향을 줍니다.

로컬 설정에는 가입 허용과 이메일 확인 비활성화가 있습니다. 운영 Supabase 설정은 확인하지 않았습니다. 이메일 소유 확인이 강제되거나 이미 신뢰된 관리자 목록이 존재하는 환경에서는 이 시나리오가 성립하지 않을 수 있습니다.

### 개선 방향

- 관리자 목록에 없는 기존 이메일 계정을 발견하면 자동 승격을 중단합니다.
- 운영자가 소유권 확인을 마친 `auth_user_id`를 명시적으로 지정하는 절차를 사용합니다.
- 최초 관리자 생성 전 공개 가입 정책을 제한하고 이메일 소유 확인을 점검합니다.
- 이미 등록된 신뢰된 관리자에 대한 재실행 동작을 명확히 정의합니다.

### 완료 판단

- [ ] 일반 기존 계정은 이메일 일치만으로 관리자가 되지 않는다.
- [ ] 운영자가 확인한 ID로만 기존 계정 등록이 가능하다.
- [ ] 신규 관리자 생성과 신뢰된 관리자 재실행 시나리오를 검증했다.
- [ ] 운영 signup·이메일 확인 설정을 기록했다.
- [ ] 수정 커밋과 검증 결과를 아래 변경 이력에 기록했다.

실제 계정 생성, 관리자 변경 또는 운영 Auth 설정 조회는 수행하지 않았습니다.

## SEC-003: 유효한 DB 설정에 따라 PostgreSQL 인증서 검증 비활성화

- 원본 finding ID: `csf_62451bfe93f74a743abec1d3`.
- 근거: [DB 풀 설정](../../backend/src/core/db.ts) 11행, [환경 설정](../../backend/src/core/config.ts) 80–81행, [Render 설정](../../render.yaml) 21–22행.

### 원인과 성립 조건

`DATABASE_SSL=require`이면 풀에 `ssl: { rejectUnauthorized: false }`를 전달합니다. 이 설정이 실제 연결에 남으면 TLS 암호화를 사용해도 서버 인증서를 검증하지 않아 네트워크 중간자에게 DB 자격 증명·데이터가 노출될 수 있습니다.

다만 접속 URL의 SSL 옵션이 풀 설정을 덮어쓸 수 있습니다. 검토 당시 설치된 `pg@8.23.0`과 `pg-connection-string@2.14.0`에서는 URL에 `sslmode=require` 또는 `verify-full`이 있고 libpq compatibility 옵션이 없으면 기본 인증서 검증이 적용됩니다. 저장소 README의 접속 예시에도 `sslmode=require`가 있습니다.

따라서 운영 DB 인증서 검증이 실제로 꺼져 있다고 확정할 수 없습니다. 실제 URL·옵션 우선순위·배포 의존성 버전을 확인해야 합니다. 악용에는 유효한 비검증 구성과 네트워크 가로채기 능력이 함께 필요합니다.

### 개선 방향

- `rejectUnauthorized: false`를 제거하고 신뢰할 수 있는 CA와 호스트 이름 검증을 적용합니다.
- URL과 풀 SSL 옵션의 우선순위 및 허용 구성을 통일합니다.
- 인증서 검증이 비활성화된 운영 구성은 시작 시 거부합니다.
- lockfile 기반 설치로 검토한 파서 버전과 배포 버전을 맞춥니다.

### 완료 판단

- [ ] 운영의 유효한 TLS 설정과 배포 pg 버전을 확인했다.
- [ ] 정상 인증서 연결이 성공한다.
- [ ] 잘못된 CA·호스트 이름·만료 인증서를 사용하는 격리 환경의 연결이 거부된다.
- [ ] 개발 환경의 허용 정책을 명시하고 운영에서 검증 우회를 차단했다.
- [ ] 수정 커밋과 검증 결과를 아래 변경 이력에 기록했다.

운영 DB 연결이나 인증서 테스트는 수행하지 않았습니다.

## 확인된 보호 장치와 검토 한계

- 관리자 라우트는 Supabase `getUser` 검증과 활성 관리자 목록의 `auth_user_id`를 확인합니다.
- 시험 세션 토큰은 해시와 상수 시간 비교로 확인하며, 마라톤은 세션과 브라우저 소유권을 함께 검증합니다.
- 결과 링크 토큰은 URL fragment로 전달하고 만료·취소 상태를 검사합니다.
- SQL은 파라미터 바인딩을 사용하며 FFmpeg는 shell 대신 인수 배열로 실행합니다.
- React의 기본 텍스트 이스케이프를 확인했고 소스 기반 XSS·인증 우회·SQL injection·다른 사용자 데이터 접근·RCE·SSRF 경로는 확인하지 못했습니다.
- localStorage 사용, 관리자 코드의 브라우저 포함, RLS 부재만으로 취약점이라고 판정하지 않았습니다. 로컬 Supabase API 스키마에는 topik_app/topik_bank가 포함되지 않습니다.
- 위 보호 장치는 안전성 보증이 아닙니다. 배포 설정과 향후 변경은 재검토해야 합니다.

## 지속 관리 방법

1. 기존 항목은 ID를 유지하고 상태를 `미수정 → 진행 중 → 수정됨·검증 대기 → 완료`로 갱신합니다. 운영 확인 과제는 확인한 구성과 날짜를 남깁니다.
2. 새 항목은 SEC/HARD ID, 발견 커밋, 진입점, 공격자 조건, 영향, 코드 근거, 개선 방향 및 완료 기준을 기록합니다.
3. 완료는 수정 커밋과 실제 검증 결과가 있는 경우에만 표시합니다. 정적 검토와 실행 검증을 구분합니다.
4. 비밀키·실제 접속 URL·개인정보 대신 환경변수 이름과 익명화한 증거를 남깁니다.
5. 이 폴더의 자료는 Git으로 공유·백업되지 않으므로 필요한 경우 별도 로컬 백업을 사용합니다.
